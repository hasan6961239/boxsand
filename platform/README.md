# سُفرة — منصة إدارة المنيو الرقمي للمطاعم

منصة **متعددة المستأجرين** (Multi-Tenant): كل مطعم ينشئ منيوه الإلكتروني، ويحصل
على رابط خاص ورمز QR ثابت، ويدير أصنافه وأسعاره وشكاوى زبائنه من لوحة تحكم
بسيطة — بينما تدير أنت المنصة كلها من لوحة إدارة واحدة.

> تُبنى مرة واحدة، ثم كل مطعم جديد هو صف في قاعدة البيانات: لا نشر جديد ولا كود
> جديد لكل عميل.

## ١) نظرة عامة

```
صاحب المطعم يسجّل  →  يبني منيوه من لوحة التحكم  →  رابط + رمز QR ثابت
                                                          ↓
                          الزبون يمسح الرمز  →  منيو فوري على الهاتف، بلا تطبيق
                                                          ↓
                                    شكاوى واقتراحات تعود إلى لوحة صاحب المطعم
```

**ثلاثة أدوار:**

| الدور | ماذا يرى | كيف يُفرض العزل |
|---|---|---|
| **مدير المنصة** | كل المطاعم والمستخدمين والشكاوى والخطط | `is_super_admin()` داخل قاعدة البيانات |
| **صاحب المطعم** | مطعمه وحده | سياسات RLS على كل جدول |
| **الزبون** | المنيو المنشور فقط | `get_public_menu()` تحدّد الحقول بالاسم |

## ٢) المزايا

**صفحة المنيو (الأهم):** غلاف وشعار، شارة «مفتوح الآن» محسوبة بتوقيت المطعم،
أزرار اتصال وواتساب وخرائط وتواصل اجتماعي، شريط عروض، أقسام لاصقة تتبع التمرير،
بحث فوري مؤجَّل، تصفية (عروض / الأكثر طلباً / جديد / نباتي)، بطاقات أصناف بحركة
ظهور متدرّجة، ورقة تفاصيل بالأحجام والإضافات وحساب السعر، وضع ليلي، ونموذج شكاوى
بتقييم اختياري.

**لوحة المطعم:** معالج إعداد، معلومات المطعم، أوقات عمل بفترات متعددة تدعم ما بعد
منتصف الليل، ستة ثيمات مع تخصيص كامل ومعاينة حيّة، أقسام وأصناف بالسحب والإفلات،
أحجام وإضافات، عروض، رفع صور مضغوطة تلقائياً، تبديل التوفر بنقرة، شكاوى بحالات
وبحث، رمز QR للطباعة، وإحصائيات.

**لوحة الإدارة:** ملخّص المنصة، جدول المطاعم بعدّاداته وتعطيله وتفعيله وحذفه،
المستخدمون وحظرهم، الشكاوى على مستوى المنصة، تحرير الخطط وحدودها، وإعدادات المنصة
بما فيها إغلاق التسجيل الذاتي.

**عرضياً:** SEO ديناميكي وOpen Graph وبيانات Schema.org منظَّمة، خريطة موقع تشمل
منيو كل مطعم، إحصائيات بلا كوكيز تتبع، تحديد معدل على الشكاوى، حالات فارغة وتحميل
وخطأ لكل شاشة، ودعم `prefers-reduced-motion`.

## ٣) المعمارية

```
┌──────────────────────────────────────────────────────────────┐
│  متصفح الزبون  ·  متصفح صاحب المطعم  ·  متصفح المدير          │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS
┌───────────────────────────▼──────────────────────────────────┐
│  Netlify — Next.js 15 App Router                              │
│                                                               │
│  /menu/[slug]   مكوّن خادم + ISR ٦٠ث  → HTML كامل، لا دوّارة   │
│  /r/[shortId]   تحويل مؤقت إلى المنيو الحالي (ثبات رمز QR)    │
│  /dashboard     force-dynamic، جلسة المستخدم                  │
│  /admin         force-dynamic، صلاحية مدير المنصة             │
│  /api/*         استقبال الشكاوى وتسجيل المشاهدات              │
│  middleware     تجديد الجلسة + حراسة المسارات                 │
└───────────────────────────┬──────────────────────────────────┘
                            │ مفتاح anon للمستخدم · مفتاح الخدمة على الخادم فقط
┌───────────────────────────▼──────────────────────────────────┐
│  Supabase — PostgreSQL + Auth + Storage                       │
│                                                               │
│  ★ RLS على ٢٠ جدولاً — العزل مفروض هنا لا في الواجهة          │
│  ★ get_public_menu(slug)   دالة SECURITY DEFINER تُرجع JSON    │
│     نظيفاً: لا owner_id، لا حقول داخلية، لا مخفيات            │
│  ★ مشغّلات تمنع ربط صف بأبٍ يتبع مطعماً آخر                    │
│  ★ hit_rate_limit()  عدّاد في القاعدة لا في ذاكرة الخادم       │
└──────────────────────────────────────────────────────────────┘
```

**لماذا الطلب العام لا يقرأ الجداول مباشرة؟** لأن دالة واحدة تُرجع كل ما تحتاجه
صفحة المنيو في رحلة واحدة، وتحدّد الحقول بالاسم — فلا يتسرّب حقل داخلي حتى لو
أخطأنا لاحقاً في الواجهة.

**لماذا تحديد المعدل في قاعدة البيانات؟** لأن كل استدعاء على Netlify قد يقع في
نسخة مختلفة من الدالة، فالعدّاد في الذاكرة يُصفَّر عملياً عند كل طلب.

| الطبقة | الاختيار | لماذا |
|---|---|---|
| الإطار | **Next.js 15 (App Router) + TypeScript** | المنيو يُصيَّر على الخادم فيفتح سريعاً؛ وServer Actions تعطي Backend حقيقياً بلا API منفصل |

| الحركات | **Motion** للأوراق المنزلقة، **CSS** لبطاقات الأصناف | مكوّن حركة لكل بطاقة يعني مئات المكوّنات الحيّة في منيو كبير |

| الترتيب | **dnd-kit** | يعمل باللمس وRTL ولوحة المفاتيح |
| التحقق | **Zod** | مخطط واحد للعميل والخادم |

| الاختبار | **Vitest** + **Playwright** + ثلاث مجموعات على Postgres حقيقي | وحدات، ومسارات، وعزل، ورحلة كاملة، وهجمات |
| النشر | **Netlify** + `@netlify/plugin-nextjs` | |

## ٧) متغيّرات البيئة

**لا تضع أي مفتاح حقيقي في Git.** القيم الحقيقية تذهب إلى `.env.local` محلياً
(وهو مستثنى من Git)، وإلى إعدادات Netlify في الإنتاج.

### مطلوبة

| المتغيّر | من أين | ملاحظة |
|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | أنت تحدده | ⚠ **اضبطه على دومينك قبل طباعة أي رمز QR** |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase ← Project Settings ← Data API | |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | نفس المكان | عام وآمن — محكوم بالكامل بـ RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | Project Settings ← API | ⚠ يتجاوز كل السياسات. خادمي فقط |
| `ANALYTICS_SALT` | ولّده أنت | ملح تجزئة الزوار اليومية |

```bash
# توليد الملح
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

### للسكربتات المحلية فقط (لا تُضاف إلى Netlify)

`SUPABASE_DB_URL` للهجرات · `SEED_DEMO_EMAIL` و`SEED_DEMO_PASSWORD` للبذور ·
`ADMIN_EMAIL` و`ADMIN_PASSWORD` و`ADMIN_NAME` لإنشاء المدير.

> **لماذا `NEXT_PUBLIC_SITE_URL` حرج؟** رمز QR يحمل هذا العنوان داخله. لو طُبع
> وهو `localhost` لن يعمل على أي هاتف، ولن يُصلَح بعد لصق الملصقات على الطاولات.
> لذلك صفحة QR تمنع التنزيل والطباعة وتعرض تحذيراً أحمر إن لم يكن مضبوطاً.

## ٨) إعداد Supabase

### أ. قاعدة البيانات والهجرات

```bash
npm run db:push
```

السكربت يحتفظ بجدول `schema_migrations`، فيطبّق الجديد فقط ويتخطّى ما طُبّق —
شغّله بأمان بعد كل تحديث.

**الجداول (٢٠ جدولاً، ١٤ هجرة):**

```
profiles ──┬─< restaurants ──┬── restaurant_themes (١:١)
           │                 ├─< restaurant_slugs      ← الروابط القديمة تبقى تعمل
           │                 ├─< restaurant_members    ← الموظفون / الفروع
           │                 ├─< opening_hours         ← فترات متعددة في اليوم
           │                 ├─< categories ──< products ──┬─< product_variants
           │                 │                             └─< option_groups ──< options
           │                 ├─< offers
           │                 ├─< complaints
           │                 ├─< analytics_daily  +  product_views_daily
           │                 └─── subscriptions >── plans
           └─< audit_logs
platform_settings (صف واحد)    rate_limits (مؤقت)    analytics_visitors (تجزئات يومية)
```

**جداول لم تُضف عمداً:** لا `qr_codes` — الرمز مشتق من `restaurants.short_id`
الثابت. ولا `notifications` — الإشعار الوحيد حالياً عدّاد الشكاوى غير المقروءة.

### ب. المصادقة

في **Supabase ← Authentication**:

1. **URL Configuration ← Site URL:** دومينك (أو `http://localhost:3000` محلياً).
2. **Redirect URLs:** أضف `https://دومينك/auth/callback`.
3. **Providers ← Email:** مفعّل، واترك **Confirm email** مفعّلاً.
4. للإنتاج: اربط مزوّد SMTP من **Project Settings ← Auth ← SMTP Settings** —
   البريد المدمج محدود العدد ومخصّص للتجربة.

### ج. التخزين

الهجرة `0010_storage.sql` تنشئ الدلو والسياسات تلقائياً. تحقّق في
**Supabase ← Storage** من وجود `restaurant-media` عاماً بحد ٢ ميجابايت.

مسار كل ملف يبدأ بمعرّف المطعم (`{restaurant_id}/products/xxx.webp`) والسياسة
تقرأ هذا الجزء — فلا يستطيع مطعم الكتابة في مجلد غيره. والصور تُضغط وتُحوَّل
WebP **في متصفح صاحب المطعم قبل الرفع**.

## ١١) حسابات الدخول

**لا توجد كلمات مرور في المستودع.** تُنشأ الحسابات بسكربتات تأخذ القيم من سطر
الأوامر أو من متغيّرات البيئة.

### مدير المنصة (Super Admin)

```bash
npm run create:admin -- \
  --email you@example.com \
  --password "كلمة-مرور-قوية-جداً" \
  --name "اسمك"
```

ثم سجّل الدخول وافتح `/admin`. السكربت ينشئ الحساب إن لم يكن موجوداً، ويرقّي
الموجود.

### صاحب مطعم (Restaurant Owner)

طريقتان:

**١) تسجيل ذاتي** — افتح `/register` واملأ النموذج. هذا ما سيفعله عملاؤك.

**٢) الحساب التجريبي** — يُنشئه `npm run db:seed`:

```bash
# كلمة مرور من اختيارك:
SEED_DEMO_PASSWORD="كلمة-مرور-قوية" npm run db:seed

# أو اتركها فارغة فتُولَّد عشوائياً وتُطبع مرة واحدة:
npm run db:seed
```

يطبع السكربت البريد وكلمة المرور في نهايته. **احفظها — لن تُعرض مرة أخرى.**

## ١٣) الاختبارات

```bash
npm run test          # ٩٢ اختبار وحدة
npm run test:db       # ٦٧ اختبار عزل على PostgreSQL حقيقي
npm run test:journey  # ٥١ خطوة — رحلة صاحب المطعم كاملة
npm run test:attack   # ٦٨ محاولة اختراق
npm run test:e2e      # ٢٤ اختبار مسار في متصفح حقيقي
npm run test:all      # الأنواع + القواعد + الوحدات + الثلاثة الأخيرة
```

**اختبارات قاعدة البيانات** تعمل على PostgreSQL محلي مؤقت (`scripts/local-db.mjs`)
مع محاكاة صغيرة لمخطط `auth`، فتُطبَّق الهجرات نفسها حرفياً:

- **العزل** (`db-test`) — لا تقرأ السياسات بل تحاول اختراقاً فعلياً.
- **الرحلة** (`db-journey`) — تسجيل ← مطعم ← أقسام ← أصناف ← إخفاء وترتيب ←
  QR ← شكوى ← إيقاف وإعادة تفعيل، بهوية المستخدم وتحت RLS.
- **الهجمات** (`db-attack`) — تسعة محاور: الكتابة عبر المفاتيح الأجنبية، التعديل
  والحذف، القراءة، تصعيد الصلاحية، الزائر، كشف المحتوى غير المنشور، المطاعم
  الموقوفة، حقن المدخلات، ومسارات رفع الملفات.

**اختبارات المسارات** تعمل على بناء إنتاجي، وتتخطّى ما يحتاج قاعدة بيانات بوضوح
حين تكون المتغيّرات غائبة. لتغطية Safari: `npx playwright install webkit` ثم أضف
مشروعاً بـ `devices['iPhone 13']`.

**Site configuration ← Environment variables**، أضف الخمسة المطلوبة من القسم ٧.

اترك `NEXT_PUBLIC_SITE_URL` مؤقتاً على عنوان Netlify الذي ستحصل عليه

### الخطوة ٥ — أكمل إعداد Supabase

1. **Authentication ← URL Configuration ← Site URL** = عنوان موقعك.
2. **Redirect URLs** ← أضف `https://دومينك/auth/callback`.

### الخطوة ٦ — تحقّق

| الرابط | المتوقَّع |
|---|---|
| `/` | الصفحة الرئيسية |
| `/menu/demo` | المنيو التجريبي |

## ١٦) الأمان وعزل المستأجرين

### ثلاث طبقات

1. **RLS في Postgres** — كل جدول عليه سياسات. حتى لو تسرّب مفتاح `anon` كاملاً
   لا يقرأ أحد بيانات مطعم لا يملكه ولا يكتب فيه.
2. **Server Actions** تتحقق من الملكية قبل كل كتابة، والمدخلات تمر بـ Zod.
3. **Middleware** يمنع الوصول للصفحات — طبقة راحة لا طبقة أمان.

### قرارات مقصودة

- **سياسات القراءة العامة موجَّهة إلى `anon` وحده.** السياسات تُجمَع بـ OR، فلو
  شملت المستخدم المسجَّل لرأى صاحب مطعم أصناف كل المطاعم المنشورة في أي استعلام
  ينسى تقييده بمعرّف مطعمه.
- **مشغّلات تمنع ربط صف بأبٍ يتبع مطعماً آخر.** جداول الأحجام والإضافات تحمل
  `restaurant_id` للسياسة و`product_id` للربط؛ فحص الأول وحده كان يسمح لصاحب
  مطعم بإلحاق صف بصنف في مطعم آخر — وتغيير سعره عبر مشغّل المزامنة.
- **الزائر لا يملك صلاحية إدراج الشكاوى.** RLS لا تستطيع تنفيذ تحديد معدل، ولو
  فُتح الإدراج لأمكن إغراق أي مطعم بآلاف الرسائل عبر REST API مباشرة.
- **سُحبت صلاحية التنفيذ من `PUBLIC`** عن دوال الإحصائيات والإدارة.
- **الحالة والملكية ملك للمنصة:** حارس على مستوى الصف يمنع صاحب المطعم من رفع
  حالته أو نقل ملكيته أو ترقية نفسه.
- **سجل العمليات لا يقبل الكتابة إلا من مدير المنصة**، والدالة تثبّت هوية الفاعل
  من الجلسة ولا تقبلها من المستدعي.
- **عناوين الصور مقيّدة** بدلو Supabase أو مسار محلي.
- **JSON-LD مهرَّب** — اسم مطعم يحتوي `</script>` كان ينهي الوسم مبكراً.
- **لا تخزين مؤقت للوحات** — `force-dynamic` على `/dashboard` و`/admin`.

### الخصوصية

لا كوكيز تتبع ولا تخزين لعناوين IP. الزائر يُمثَّل بتجزئة يومية غير قابلة للعكس
(عنوان + متصفح + ملح سري + تاريخ اليوم) تفقد معناها عند منتصف الليل وتُحذف بعد
يومين. والإحصائيات مجمَّعة يومياً لا صفاً لكل زيارة.

## ١٧) حلّ المشكلات

| العَرَض | السبب والحل |
|---|---|
| البناء يفشل بـ `NEXT_PUBLIC_SUPABASE_URL is not defined` | المتغيّرات غير مضافة في Netlify. أضفها ثم **Clear cache and deploy**. |
| صفحة بيضاء بعد النشر | **Base directory** ليس `platform`. صحّحه وأعد النشر. |
| صفحة QR تعرض تحذيراً أحمر ولا تسمح بالطباعة | `NEXT_PUBLIC_SITE_URL` غير مضبوط. اضبطه وأعد النشر — هذا الحارس يمنع طباعة رموز معطّلة. |
| رابط تفعيل البريد يفتح `localhost` | **Site URL** في Supabase ما زال محلياً. |
| «انتهت صلاحية الرابط» عند التفعيل | الرابط يُستعمل مرة واحدة وينتهي بعد ساعة. اطلب إرسالاً جديداً. |
| المنيو يظهر «غير متاح» | حالة المطعم `suspended` أو `disabled`. غيّرها من `/admin/restaurants`. |
| رفع الصورة يفشل | الدلو غير موجود أو الصورة أكبر من ٥ م.ب. شغّل `npm run db:push` وتحقّق من Storage. |
| الصور لا تظهر | `NEXT_PUBLIC_SUPABASE_URL` مفقود وقت البناء فلم يُسجَّل النطاق في `next.config.ts`. أضفه وأعد البناء. |
| تعديلات المنيو لا تظهر للزبون | المنيو مخزَّن ٦٠ ثانية ويُجدَّد عند الحفظ. انتظر قليلاً أو أعد التحميل بقوة. |
| الإحصائيات صفر | التتبّع يعمل على الزيارات العامة فقط، ويُحدَّث بعد أول زيارة حقيقية. |
| `npm run test:db` يفشل | يحتاج PostgreSQL 16 محلياً. حدّد مساره بـ `SUFRA_PG_BIN`. |
| «بلغت الحد الأقصى» | حدود الخطة. ارفعها من `/admin/plans` أو رقِّ خطة المطعم. |
| Playwright يشكو من متصفح ناقص | `npx playwright install chromium`، أو حدّد متصفحاً مثبَّتاً بـ `PLAYWRIGHT_CHROMIUM_PATH`. |

## ١٨) تحسينات مستقبلية

البنية جاهزة لهذه دون إعادة كتابة:

- **الطلب الإلكتروني والسلة** — الأحجام والإضافات وحساب السعر موجودة فعلاً في
  ورقة تفاصيل الصنف.
- **طلب عبر واتساب** — تجميع الاختيارات في رسالة جاهزة.
- **رمز QR لكل طاولة** — عمود واحد إضافي.
- **الموظفون** — `restaurant_members` بأدواره جاهز، تنقصه واجهة الدعوات.
- **الفروع** — المستخدم يملك أكثر من مطعم أصلاً؛ ينقص مبدّل في اللوحة.
- **بوابة الدفع** — `plans` و`subscriptions` جاهزان.
- **الإنجليزية** — كل النصوص في مكوّنات؛ إضافة `next-intl` عمل يوم واحد.
- **نطاق فرعي لكل مطعم** — `slug` موجود؛ يحتاج توجيهاً في الـ middleware.
- **إشعارات فورية**، **شاشة المطبخ**، **برنامج الولاء**، **الحجوزات**.
- **PWA كاملة** — الملف والأيقونات موجودة، ينقص Service Worker.
