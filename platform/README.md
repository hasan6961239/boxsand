# سُفرة — منصة إدارة المنيو الرقمي للمطاعم

منصة **متعددة المستأجرين** (Multi-Tenant) يُنشئ فيها كل مطعم منيوه الإلكتروني،
ويحصل على رابط خاص ورمز QR، ويدير أصنافه وأسعاره وشكاوى زبائنه من لوحة تحكم
بسيطة — بينما تدير أنت المنصة كلها من لوحة إدارة واحدة.

> تُبنى مرة واحدة، ثم كل مطعم جديد هو صف في قاعدة البيانات: لا نشر جديد ولا كود
> جديد لكل عميل.

## ١) نظرة عامة

```
صاحب المطعم يسجّل  →  يبني منيوه من لوحة التحكم  →  رابط ثابت + رمز QR
                                                          ↓
                          الزبون يمسح الرمز  →  منيو فوري على الهاتف، بلا تطبيق
                                                          ↓
                                    شكاوى واقتراحات تعود إلى لوحة صاحب المطعم
```

**ثلاثة أدوار:**

| الدور | ماذا يرى | كيف يُفرض العزل |
|---|---|---|
| **مدير المنصة** | كل المطاعم والمستخدمين والشكاوى والخطط | دالة `is_super_admin()` داخل قاعدة البيانات |
| **صاحب المطعم** | مطعمه وحده | سياسات RLS على كل جدول |
| **الزبون** | المنيو المنشور فقط | دالة `get_public_menu()` تحدّد الحقول بالاسم |

## ٢) المزايا

**صفحة المنيو (الأهم):** غلاف وشعار، شارة «مفتوح الآن» محسوبة بتوقيت المطعم،
أزرار اتصال وواتساب وخرائط وتواصل اجتماعي، شريط عروض، أقسام لاصقة تتبع التمرير،
بحث فوري مؤجَّل، تصفية (عروض / الأكثر طلباً / جديد / نباتي)، بطاقات أصناف بحركة
ظهور متدرّجة، ورقة تفاصيل بالأحجام والإضافات وحساب السعر، وضع ليلي، ونموذج شكاوى
بتقييم اختياري.

**لوحة المطعم:** معالج إعداد، معلومات المطعم، أوقات عمل بفترات متعددة تدعم ما بعد
منتصف الليل، ستة ثيمات مع تخصيص كامل ومعاينة حيّة، أقسام وأصناف بالسحب والإفلات،
أحجام وإضافات، عروض، رفع صور مضغوطة تلقائياً، تبديل التوفر بنقرة، شكاوى بحالات
وبحث، رمز QR للطباعة، وإحصائيات.

**لوحة الإدارة:** ملخّص المنصة، جدول المطاعم بعدّاداته وتعطيله وتفعيله وحذفه،
المستخدمون وحظرهم، الشكاوى على مستوى المنصة، تحرير الخطط وحدودها، وإعدادات المنصة
بما فيها إغلاق التسجيل الذاتي.

**عرضياً:** SEO ديناميكي وOpen Graph وبيانات Schema.org منظَّمة، خريطة موقع تشمل
منيو كل مطعم، إحصائيات بلا كوكيز تتبع، تحديد معدل على الشكاوى، حالات فارغة وتحميل
وخطأ لكل شاشة، ودعم `prefers-reduced-motion`.

## ٣) التقنيات

| الطبقة | الاختيار | لماذا |
|---|---|---|
| الإطار | **Next.js 15 (App Router) + TypeScript** | صفحة المنيو تُصيَّر على الخادم فتفتح سريعاً؛ وServer Actions تعطي Backend حقيقياً بلا API منفصل |
| التنسيق | **Tailwind CSS v4** + متغيّرات CSS | ثيم كل مطعم متغيّرات تُحقن على عنصر واحد، لا ملف CSS لكل مطعم |
| قاعدة البيانات | **Supabase** (Postgres + Auth + Storage) | RLS يحل العزل من جذره، والخطة المجانية تكفي عشرات المطاعم |
| الحركات | **Motion** (Framer Motion) | `whileInView` بميزانية محدودة، واحترام تقليل الحركة |
| QR | **qrcode** | SVG وPNG بجودة طباعة |
| الترتيب | **dnd-kit** | يعمل باللمس وRTL ولوحة المفاتيح |
| التحقق | **Zod** | مخطط واحد للعميل والخادم |
| المخططات | **Recharts** | خفيف وكافٍ |
| الخط | **Tajawal** مستضاف ذاتياً | لا طلب خارجي، وتقسيم unicode-range يحمّل ~٣٧ ك.ب للعربية |
| الاختبار | **Vitest** + **Playwright** + أداة اختبار RLS | وحدات ومسارات حرجة وعزل حقيقي |
| النشر | **Netlify** + `@netlify/plugin-nextjs` | كما هو مطلوب |

**لماذا Netlify + Supabase ولماذا ليس موقعاً ثابتاً؟** لأن المشروع يحتاج مصادقة
حقيقية وصلاحيات مفروضة على الخادم. Netlify تشغّل Next.js كدوال بلا خادم، وSupabase
تعطي Postgres مُداراً بسياسات صفّية — فينتج نظام حقيقي بتكلفة صفر في البداية
وقابل للتوسع.

## ٥) التشغيل المحلي

```bash
cd platform
npm install
cp .env.example .env.local     # ثم املأ القيم — انظر القسم التالي
npm run db:push                # يطبّق الهجرات على مشروع Supabase
npm run db:seed                # مطعم تجريبي على /menu/demo
npm run dev                    # http://localhost:3000
```

**المتطلبات:** Node.js 20.9 أو أحدث، ومشروع Supabase مجاني.

أوامر أخرى:

```bash
npm run build       # بناء الإنتاج

npm run test:e2e    # المسارات الحرجة
npm run test:all    # الأنواع + الوحدات + العزل
```

## ٦) متغيرات البيئة

انسخ `.env.example` إلى `.env.local`. **لا تضع أي مفتاح حقيقي في مستودع Git.**

| المتغير | أين تجده | لماذا |
|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | أنت تحدده | يدخل في روابط QR ووسوم المشاركة وخريطة الموقع. **اضبطه على دومينك قبل طباعة أي رمز.** |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase ← Project Settings ← Data API | عنوان المشروع |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | نفس المكان | مفتاح عام، محكوم بالكامل بسياسات RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | Project Settings ← API | **يتجاوز كل السياسات.** لا يُقرأ إلا في كود الخادم، ولا يبدأ اسمه بـ `NEXT_PUBLIC_` |
| `SUPABASE_DB_URL` | Project Settings ← Database ← URI | للهجرات والبذور فقط (سكربتات npm)، لا يحتاجه التطبيق |
| `ANALYTICS_SALT` | ولّده أنت | ملح تجزئة الزوار اليومية |

```bash
# توليد ملح عشوائي
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

## ٧) إعداد قاعدة البيانات

١. أنشئ مشروعاً على [supabase.com](https://supabase.com) (الخطة المجانية تكفي).
٢. انسخ `SUPABASE_DB_URL` إلى `.env.local`.
٣. طبّق الهجرات:

```bash
npm run db:push
```

السكربت يحتفظ بجدول `schema_migrations`، فيطبّق الجديد فقط ويتخطّى ما طُبّق —
تستطيع تشغيله بأمان بعد كل تحديث.

### الجداول

```
profiles ──┬─< restaurants ──┬── restaurant_themes (١:١)
           │                 ├─< restaurant_slugs      ← الروابط القديمة تبقى تعمل
           │                 ├─< restaurant_members    ← الموظفون / الفروع
           │                 ├─< opening_hours         ← فترات متعددة في اليوم
           │                 ├─< categories ──< products ──┬─< product_variants
           │                 │                             └─< option_groups ──< options
           │                 ├─< offers
           │                 ├─< complaints
           │                 ├─< analytics_daily  +  product_views_daily
           │                 └─── subscriptions >── plans
           └─< audit_logs
platform_settings (صف واحد)    rate_limits (مؤقت)
```

**جداول لم تُضف عمداً:** لا جدول `qr_codes` — الرمز مشتق من `restaurants.short_id`
الثابت. ولا جدول `notifications` — الإشعار الوحيد حالياً هو عدّاد الشكاوى غير
المقروءة.

## ٨) إعداد المصادقة

في **Supabase ← Authentication**:

١. **URL Configuration ← Site URL:** ضع دومينك (أو `http://localhost:3000`).
٢. **Redirect URLs:** أضف `https://دومينك/auth/callback`.
٣. **Providers ← Email:** مفعّل. اترك **Confirm email** مفعّلاً (موصى به).
٤. **Email Templates:** عرّبها إن شئت — الروابط تعمل كما هي.

> البريد المدمج في Supabase محدود العدد ومخصّص للتجربة. للإنتاج اربط مزوّد SMTP
> من **Project Settings ← Auth ← SMTP Settings**.

## ٩) إعداد التخزين

الهجرة `0010_storage.sql` تنشئ الدلو والسياسات تلقائياً. تحقّق فقط في
**Supabase ← Storage** من وجود دلو `restaurant-media` عام بحد ٢ ميجابايت.

مسار كل ملف يبدأ بمعرّف المطعم (`{restaurant_id}/products/xxx.webp`) والسياسة
تقرأ هذا الجزء — فلا يستطيع مطعم الكتابة في مجلد مطعم آخر ولا حذف صوره.

الصور تُضغط وتُحوَّل إلى WebP **في متصفح صاحب المطعم قبل الرفع**، فتوفّر عرض
النطاق مرتين: عند الرفع وعند كل مشاهدة.

## ١٢) النشر على Netlify

### أ. اربط المستودع

١. **Add new site ← Import an existing project** واختر المستودع.
٢. اضبط الإعدادات:

| الحقل | القيمة |
|---|---|
| **Base directory** | `platform` |
| **Build command** | `npm run build` |
| **Publish directory** | `platform/.next` |

> **مهم:** هذا المستودع يحتوي مشروعاً آخر في جذره، لذلك **Base directory** إلزامي.
> ملف `platform/netlify.toml` يضبط الباقي (الإضافة، نسخة Node، ترويسات التخزين).

### ب. أضف متغيرات البيئة

**Site configuration ← Environment variables**، أضف الستة من القسم ٦.
اضبط `NEXT_PUBLIC_SITE_URL` على دومين Netlify (أو دومينك الخاص).

### ج. انشر

اضغط **Deploy site**. البناء الأول يستغرق دقيقتين تقريباً.

### د. بعد النشر

١. أضف `https://دومينك/auth/callback` إلى **Redirect URLs** في Supabase.
٢. حدّث `NEXT_PUBLIC_SITE_URL` وأعد النشر إن غيّرت الدومين.
٣. جرّب: `/` ثم `/menu/demo` ثم `/login`.

### الدومين الخاص

**Domain management ← Add a domain**، واتبع إرشادات DNS. ثم **حدّث
`NEXT_PUBLIC_SITE_URL` وأعد النشر قبل طباعة أي رمز QR**، لأن الرمز يحمل الدومين
داخله.

## ١٣) الأمان وعزل المستأجرين

### ثلاث طبقات

١. **RLS في Postgres** — كل جدول عليه سياسات. حتى لو تسرّب مفتاح `anon` كاملاً
   لا يقرأ أحد بيانات مطعم لا يملكه ولا يكتب فيه.
٢. **Server Actions** تتحقق من الملكية قبل كل كتابة، والمدخلات تمر بـ Zod.
٣. **Middleware** يمنع الوصول للصفحات — طبقة راحة لا طبقة أمان.

### قرارات مقصودة

- **سياسات القراءة العامة موجَّهة إلى `anon` وحده**، لا إلى `authenticated`.
  السياسات تُجمَع بـ OR، فلو شملت المستخدم المسجَّل لرأى صاحب مطعم أصناف كل
  المطاعم المنشورة في أي استعلام ينسى تقييده بمعرّف مطعمه.
- **المنيو العام يُخدَم بدالة `SECURITY DEFINER`** تحدّد الحقول بالاسم، فلا
  يتسرّب `owner_id` ولا أي حقل داخلي حتى لو أخطأنا لاحقاً في الواجهة.
- **الزائر لا يملك صلاحية إدراج الشكاوى.** RLS لا تستطيع تنفيذ تحديد معدل، ولو
  فُتح الإدراج لأمكن إغراق أي مطعم بآلاف الرسائل عبر REST API مباشرة. النموذج
  يمرّ بمسار خادمي يتحقق ويحدّ المعدل ثم يكتب.
- **سُحبت صلاحية التنفيذ من `PUBLIC`** عن دوال الإحصائيات، وإلا استطاع أي زائر
  تزوير أرقام أي مطعم.
- **الحالة والملكية ملك للمنصة:** لا يرفع صاحب مطعم نفسه من `trial` إلى `active`،
  ولا يرقّي نفسه إلى مدير — حارس على مستوى الصف يمنع ذلك.
- **سجل العمليات لا يقبل الكتابة المباشرة:** تمرّ بدالة تثبّت هوية الفاعل من
  الجلسة ولا تقبلها من المستدعي.
- **عناوين الصور مقيّدة** بدلو Supabase أو مسار محلي، فلا يستطيع أحد تحميل موارد
  من خادم غريب في متصفح كل زبون.
- **JSON-LD مهرَّب:** اسم مطعم يحتوي `</script>` كان ينهي الوسم مبكراً.
- **لا تخزين مؤقت للوحات:** `force-dynamic` على `/dashboard` و`/admin`، وإلا
  خُدّمت صفحة واحدة لكل المستخدمين حين تغيب المتغيّرات وقت البناء.

### الخصوصية

لا كوكيز تتبع ولا تخزين لعناوين IP. الزائر يُمثَّل بتجزئة يومية غير قابلة للعكس
(عنوان + متصفح + ملح سري + تاريخ اليوم) تفقد معناها عند منتصف الليل، وتُحذف بعد
يومين. والإحصائيات مجمَّعة يومياً لا صفاً لكل زيارة.

## ١٤) الاختبارات

```bash
npm run test       # ٧٦ اختبار وحدة: أسعار، أوقات عمل، تحقق، ثيمات
npm run test:db    # ٦٦ اختبار عزل على PostgreSQL حقيقي
npm run test:e2e   # مسارات حرجة في متصفح حقيقي
```

**اختبارات العزل** لا تقرأ السياسات بل تحاول اختراقاً فعلياً: صاحب مطعم يقرأ
بيانات مطعم آخر، زائر يرسل شكوى مباشرة، مستخدم يرقّي نفسه. النجاح يعني أن قاعدة
البيانات رفضت — لا أن الواجهة أخفت الزر.

تعمل على Postgres محلي مؤقت (`scripts/local-db.mjs`) مع محاكاة صغيرة لمخطط
`auth`، فتُطبَّق الهجرات نفسها حرفياً.

**اختبارات المسارات** تعمل على بناء إنتاجي، وتتخطّى ما يحتاج قاعدة بيانات بوضوح
حين تكون المتغيّرات غائبة. لتغطية Safari فعلياً: `npx playwright install webkit`
ثم أضف مشروعاً بـ `devices['iPhone 13']`.

---

## ١٥) دليل الاستخدام

### إضافة مطعم جديد

**ذاتياً:** يفتح صاحب المطعم `/register`، يملأ بياناته واسم مطعمه، يفعّل بريده،
فيصل إلى معالج الإعداد ثم لوحته.

**يدوياً (بيع مباشر):** أغلق التسجيل الذاتي من `/admin/settings`، ثم أنشئ
المستخدم من Supabase ← Authentication ← Add user، واطلب منه الدخول لإكمال الإعداد.

### بناء المنيو

١. `/dashboard/categories` ← أضف قسماً (مثلاً «البرجر»).
٢. `/dashboard/products` ← أضف صنفاً باسمه وسعره وصورته.
٣. أضف أحجاماً إن كان للصنف أكثر من سعر، وإضافات إن أمكن.
٤. رتّب بالسحب من مقبض كل صف.

### رمز QR

`/dashboard/qr` ← نزّل SVG (للطباعة الاحترافية) أو PNG، أو اطبع مباشرة.

**الرمز ثابت إلى الأبد.** يشير إلى `/r/{short_id}` الذي يحوّل إلى المنيو الحالي،
فتستطيع تغيير اسم مطعمك ورابطه وأسعارك بلا إعادة طباعة.

نصائح: لا تطبعه بعرض أقل من ٣ سم، أسود على أبيض، بحافة بيضاء حوله، وجرّب مسحه
قبل طباعة نسخ كثيرة.

### الشكاوى

تصل إلى `/dashboard/complaints` برقم وتاريخ وحالة. غيّر الحالة من القائمة
المنسدلة، وابحث بالرقم أو الاسم أو نص الرسالة.

## ١٦) بيع النظام لعدة مطاعم

النظام **متعدد المستأجرين من أساسه**: مطعم واحد أو ألف يعملون على النشرة نفسها
وقاعدة البيانات نفسها.

**خطوات البيع:**

١. اضبط الخطط وأسعارها وحدودها من `/admin/plans` — تظهر فوراً في صفحة الأسعار.
٢. قرّر نموذج الدخول: تسجيل ذاتي (الخطة المجانية مدخل) أو بيع يدوي (أغلق التسجيل
   من `/admin/settings`).
٣. عند الاشتراك: ارفع خطة المطعم وغيّر حالته إلى `active` من `/admin/restaurants`.
٤. عند التوقف عن الدفع: «موقوف» يُخفي المنيو فوراً مع ملاحظة تظهر لصاحب المطعم.
   **لا تحذف** — الحذف لا رجعة فيه.

**الحدود مفروضة فعلياً** عند إضافة قسم أو صنف، لا في الواجهة فقط — وإلا لما
بيعت الخطط.

**الدفع غير مربوط.** البنية جاهزة (`plans` و`subscriptions`) لإضافة أي مزوّد
لاحقاً دون تعديل أي جدول.

## ١٧) حلّ المشكلات

| العَرَض | السبب والحل |
|---|---|
| البناء يفشل بـ `NEXT_PUBLIC_SUPABASE_URL is not defined` | المتغيّرات غير مضافة في Netlify. أضفها ثم **Clear cache and deploy**. |
| صفحة بيضاء بعد النشر | **Base directory** ليس `platform`. صحّحه وأعد النشر. |
| رابط تفعيل البريد يفتح `localhost` | **Site URL** في Supabase ما زال محلياً. صحّحه في URL Configuration. |
| «انتهت صلاحية الرابط» عند التفعيل | الرابط يُستعمل مرة واحدة وينتهي بعد ساعة. اطلب إرسالاً جديداً. |
| المنيو يظهر «غير متاح» | حالة المطعم `suspended` أو `disabled`. غيّرها من `/admin/restaurants`. |
| رفع الصورة يفشل | الدلو غير موجود أو الصورة أكبر من ٥ م.ب. شغّل `npm run db:push` وتحقّق من Storage. |
| الصور لا تظهر | `NEXT_PUBLIC_SUPABASE_URL` مفقود وقت البناء، فلم يُسجَّل النطاق في `next.config.ts`. أضفه وأعد البناء. |
| تعديلات المنيو لا تظهر للزبون | المنيو مخزَّن ٦٠ ثانية ويُجدَّد عند الحفظ. انتظر قليلاً أو أعد التحميل بقوة. |
| الإحصائيات صفر | التتبّع يعمل على الزيارات العامة فقط، ويُحدَّث بعد أول زيارة حقيقية. |
| `npm run db:test` يفشل | يحتاج PostgreSQL 16 محلياً. حدّد مساره بـ `SUFRA_PG_BIN`. |
| «بلغت الحد الأقصى» | حدود الخطة. ارفعها من `/admin/plans` أو رقِّ خطة المطعم. |

## ١٨) تحسينات مستقبلية

البنية جاهزة لهذه دون إعادة كتابة:

- **الطلب الإلكتروني وسلة المشتريات** — الأحجام والإضافات وحساب السعر موجودة فعلاً
  في ورقة تفاصيل الصنف.
- **طلب عبر واتساب** — تجميع الاختيارات في رسالة جاهزة.
- **رمز QR لكل طاولة** — عمود واحد إضافي.
- **الموظفون** — `restaurant_members` بأدواره جاهز، تنقصه واجهة الدعوات.
- **الفروع** — المستخدم يملك أكثر من مطعم أصلاً؛ ينقص مبدّل في اللوحة.
- **بوابة الدفع** — `plans` و`subscriptions` جاهزان.
- **الإنجليزية** — كل النصوص في مكوّنات؛ إضافة `next-intl` عمل يوم واحد.
- **نطاق فرعي لكل مطعم** — `slug` موجود؛ يحتاج توجيهاً في الـ middleware.
- **إشعارات فورية** و**شاشة المطبخ** و**برنامج الولاء** و**الحجوزات**.
- **PWA كاملة** — الملف والأيقونات موجودة، ينقص Service Worker.
