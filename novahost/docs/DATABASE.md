# NOVA HOST — قاعدة البيانات

المحرّك: **SQLite** عبر `node:sqlite` المدمجة في Node (أو `better-sqlite3` تلقائياً
إن كانت مثبتة). الملف: `data/novahost.db`.

## إعدادات المحرّك ولماذا

```sql
PRAGMA journal_mode = WAL;      -- قراءة أثناء الكتابة بلا تعارض
PRAGMA synchronous  = NORMAL;   -- كتابة أقل على فلاش الهاتف، وآمن مع WAL
PRAGMA foreign_keys = ON;       -- الحذف المتتالي يعمل فعلاً
PRAGMA busy_timeout = 5000;     -- انتظر بدل الفشل عند تزامن نادر
```

`synchronous=NORMAL` قرار مقصود: مع WAL، الخطر الوحيد هو فقدان آخر معاملة عند
انقطاع كهربائي مفاجئ — وليس تلف القاعدة. على هاتف يعمل ببطارية 5000 مللي أمبير،
الانقطاع المفاجئ شبه مستحيل، والمكسب هو كتابات أقل بكثير على الذاكرة الوامضة
(وهذا يطيل عمرها فعلياً).

## الجداول

| الجدول | الغرض |
|---|---|
| `users` | الحسابات، تجزئة كلمة المرور، القفل بعد المحاولات الفاشلة، التفضيلات |
| `sessions` | الجلسات النشطة — المعرّف هنا **تجزئة** الكوكي وليس قيمته |
| `projects` | المشاريع، الـslug، الحالة، مؤشر النشر الحالي، العدّادات |
| `deployments` | كل عملية نشر برقمها وحالتها ومدّتها وسبب فشلها |
| `domains` | النطاقات المخصصة ورمز التحقق |
| `logs` | سجلات التطبيق والنشر المعروضة في اللوحة |
| `audit_log` | من فعل ماذا ومتى |
| `security_events` | نجاح/فشل تسجيل الدخول والقفل |
| `settings` | الإعدادات القابلة للتعديل وقت التشغيل (JSON) |
| `api_keys` | محجوز لـ CLI في المرحلة الثانية |

المخطط الكامل مع التعليقات: `backend/src/db/migrations/001_init.sql`.

## العلاقات

```
users ─1──n─ sessions
users ─1──n─ projects (owner_id)
projects ─1──n─ deployments
projects ─1──n─ domains
projects ─1──n─ logs
deployments ─1──n─ logs
```

`projects.current_deployment_id` يشير إلى النشر المنشور حالياً. هو **بلا قيد
مرجعي (FK)** عن قصد: الحذف المتتالي لنشر قديم يجب ألا يتسبب في مرجع دائري أثناء
الاستعادة أو التراجع. سلامته تُحفظ داخل معاملات في `services/deploy.js`، ويُعاد
بناؤه من `current.txt` إن تلف.

## لماذا لا يوجد جدول `files`؟

طلبتَ جدول `Files`، ولم أُنشئه — وهذا قرار مقصود أشرحه بدل إخفائه:

1. **القرص هو مصدر الحقيقة.** محرر الملفات يكتب على القرص مباشرة. أي جدول ملفات
   سيصبح قديماً في اللحظة التالية، وستتعامل مع بيانات كاذبة.
2. **حجم القاعدة.** موقع فيه 800 ملف × 10 نشرات = 8000 صف لمشروع واحد. مع عشرين
   مشروعاً تصبح القاعدة أكبر من المواقع نفسها، وكل كتابة تستهلك عمر الفلاش.
3. **لا فائدة استعلامية.** لا يوجد استعلام في المنصة يحتاج SQL على مستوى الملف؛
   كل ما نحتاجه هو تصفّح مجلد — وهو ما يفعله `fs.readdir` أسرع من أي استعلام.

بدلاً من ذلك: كل نشر يحفظ `manifest.json` بجانب ملفاته (قائمة المسارات والأحجام
والتجزئات)، والعدّادات (`file_count` و`total_bytes`) مخزّنة في `deployments`
و`projects` للعرض السريع في اللوحة.

هذا يعطيك نفس ما أردتَه من جدول الملفات (سرد، أحجام، عدد) دون أي من عيوبه.

## الهجرات (Migrations)

- كل هجرة ملف SQL مرقّم في `backend/src/db/migrations/`.
- جدول `schema_migrations` يسجّل ما طُبِّق (يُنشأ تلقائياً).
- التطبيق يحدث داخل معاملة واحدة: إما تنجح الهجرة كاملة أو لا شيء يتغيّر.
- تُشغَّل تلقائياً عند الإقلاع، أو يدوياً: `npm run db:migrate`.

لإضافة هجرة: أنشئ `002_xxx.sql` ولا تعدّل `001` أبداً بعد نشره.

## النسخ الاحتياطي

```sql
VACUUM INTO 'backup.db';
```
هذه هي الطريقة الصحيحة لنسخ قاعدة SQLite **أثناء عملها**: تنتج ملفاً متسقاً
ومضغوطاً بلا إيقاف الخدمة وبلا خطر نسخ ملف WAL نصف مكتوب.

نسخ `novahost.db` بأمر `cp` أثناء التشغيل قد ينتج ملفاً تالفاً — لا تفعل ذلك.

## الاحتفاظ (Retention)

| البيانات | الافتراضي | الإعداد |
|---|---|---|
| النشرات لكل مشروع | آخر 10 | `keep_deployments` |
| السجلات | 30 يوماً | `log_retention_days` |
| الجلسات المنتهية | تُحذف عند الإقلاع وكل 6 ساعات | — |
| أحداث الأمان | 90 يوماً | `security_retention_days` |

يعمل التنظيف عند الإقلاع ثم كل ست ساعات، ودائماً خارج المسار الحرج للطلبات.
