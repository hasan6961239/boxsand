# NOVA HOST — نموذج الأمان

هذا الخادم سيكون مكشوفاً على الإنترنت. عومِل الأمان هنا كمشروع إنتاج، لا كمشروع تجريبي.

## حدود الثقة الثلاثة

```
┌── النظام (Android / Termux) ───────────────────────────────┐
│  لا تصل إليه المنصة إلا للقراءة (إحصاءات) — وبلا مدخلات    │
│  من المستخدم إطلاقاً                                        │
│                                                             │
│  ┌── المنصة (لوحة التحكم + API) ────────────────────────┐   │
│  │  تتطلب جلسة مصادَقة · CSRF · تحديد معدل             │   │
│  │                                                       │   │
│  │  ┌── المواقع المستضافة ──────────────────────────┐   │   │
│  │  │  ملفات ثابتة فقط · لا تنفيذ · أصل منفصل      │   │   │
│  │  │  لا تستطيع الوصول إلى API ولا القاعدة ولا     │   │   │
│  │  │  إلى ملفات مشروع آخر                          │   │   │
│  │  └───────────────────────────────────────────────┘   │   │
│  └───────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

**قاعدة صارمة: لا يُنفَّذ أي كود مرفوع على الخادم — أبداً.** المواقع تُقدَّم كبايتات
ثابتة. لا `eval`، ولا `child_process` بمدخلات مستخدم، ولا مفسّر PHP/Node لمحتوى مرفوع.
هذا يزيل فئة كاملة من الثغرات (RCE) من المشروع في المرحلة الأولى.

## ١) المصادقة

- **تجزئة كلمة المرور:** `scrypt` من `node:crypto`، بمعاملات `N=16384, r=8, p=1`
  (نحو 16 ميجابايت ذاكرة لكل عملية تجزئة). اخترتُ 2^14 بدل 2^15 لأن الهاتف يجب أن
  يبقى مستجيباً؛ وهي أقوى بكثير من bcrypt الافتراضي ضد الهجوم بعتاد مخصص.
- الصيغة المخزّنة: `scrypt$N$r$p$<salt-b64>$<hash-b64>` — قابلة للترقية لاحقاً بلا
  كسر الحسابات القديمة.
- المقارنة بـ `timingSafeEqual` دائماً.
- **القفل التصاعدي:** بعد 5 محاولات فاشلة يُقفل الحساب دقيقة، ثم تتضاعف المدة حتى
  15 دقيقة كحد أقصى. القفل مخزّن في القاعدة فينجو من إعادة التشغيل.
- **رسالة خطأ موحّدة** لاسم مستخدم خاطئ وكلمة مرور خاطئة، حتى لا تُعدّ المنصة
  أداةً لتعداد الحسابات.

## ٢) الجلسات

| الخاصية | القيمة | السبب |
|---|---|---|
| قيمة الكوكي | 32 بايت عشوائي (`randomBytes`) | لا يمكن تخمينه |
| المخزَّن في القاعدة | `sha256(token)` | تسريب القاعدة لا يعطي جلسات حية |
| `HttpOnly` | ✅ | لا يصل إليه JavaScript |
| `SameSite` | `Lax` | يمنع CSRF عبر المواقع مع إبقاء الروابط تعمل |
| `Secure` | تلقائي عند HTTPS | لا يُرسل عبر HTTP |
| `Domain` | **غير مضبوط** (host-only) | ⚠️ الأهم: الكوكي **لا يُرسل** إلى `slug.example.com` |
| `Path` | `/` | |
| العمر | 30 يوماً (قابل للتعديل) | |

بند `Domain` غير المضبوط هو ما يمنع موقعاً مستضافاً من رؤية جلستك حتى لو كان تحت
نفس النطاق الأب.

## ٣) CSRF

دفاع مزدوج:
1. **رمز لكل جلسة** يُرسل في ترويسة `X-CSRF-Token` مع كل طلب يغيّر حالة
   (POST/PUT/PATCH/DELETE). مخزّن في القاعدة ومرتبط بالجلسة.
2. **فحص `Origin`/`Referer`** مقابل قائمة المضيفين المسموح بهم. طلب بلا أصل
   معروف يُرفض قبل أن يصل إلى المعالج.

مع `SameSite=Lax` تصبح ثلاث طبقات مستقلة.

## ٤) تحديد المعدل (Rate Limiting)

دلاء رموز في الذاكرة، مفتاحها IP + فئة المسار:

| الفئة | الحد |
|---|---|
| `/api/auth/login` | 10 طلبات / 15 دقيقة |
| `/api/setup` | 5 طلبات / ساعة |
| الرفع والنشر | 30 / ساعة |
| باقي الـAPI | 300 / دقيقة |
| المواقع المستضافة | 600 / دقيقة لكل IP |

لماذا في الذاكرة لا في القاعدة: تحديد المعدل يجب أن يكون أرخص من الطلب نفسه.
الكتابة في SQLite عند كل طلب تُهلك الفلاش. تُعاد التهيئة عند إعادة التشغيل — مقبول،
لأن القفل التصاعدي للحساب مخزّن في القاعدة وهو خط الدفاع الدائم.

## ٥) أمان ملفات ZIP — أخطر جزء في المنصة

قارئ ZIP مكتوب خصيصاً في `backend/src/services/zip.js` ليطبّق **كل** ما يلي قبل
كتابة بايت واحد على القرص:

| الهجوم | الدفاع |
|---|---|
| **Path Traversal** (`../../etc/passwd`) | تطبيع المسار ورفض أي مدخلة تخرج عن الجذر بعد `path.resolve` |
| **مسارات مطلقة** (`/etc/passwd`) | رفض أي مدخلة تبدأ بـ `/` أو `\` |
| **مسارات ويندوز** (`C:\x`, `..\\..\\x`) | رفض الحرف `\` ومحرف القرص (`X:`) |
| **روابط رمزية داخل ZIP** | رفض أي مدخلة نوعها symlink في `external_attributes` |
| **ZIP Bomb** (نسبة انضغاط خيالية) | سقف لنسبة الفك (افتراضي 120:1) وسقف للحجم الكلي بعد الفك |
| **قنبلة عدد الملفات** | سقف لعدد المدخلات (افتراضي 5000) |
| **ملف واحد ضخم** | سقف لحجم الملف الواحد بعد الفك |
| **أسماء خبيثة** (`NUL`, `CON`, محارف تحكّم) | تنظيف الأسماء ورفض محارف التحكّم و`NUL` |
| **ZIP متداخل يخدع القارئ** | الأحجام تُقرأ من **الفهرس المركزي** لا من الترويسة المحلية |
| **ZIP64 غير متوقع** | يُكتشف ويُرفض برسالة واضحة بدل سلوك غير معرَّف |
| **امتلاء القرص أثناء الفك** | فحص المساحة الحرة قبل البدء + عدّاد تراكمي أثناء الكتابة |

عند أي خرق: تتوقف العملية فوراً، ويُحذف المجلد المؤقت، ويُسجَّل السبب الدقيق في
سجل النشر، **والموقع المنشور حالياً لا يُمس**.

## ٦) مسارات الملفات (مدير الملفات)

كل مسار قادم من المستخدم يمر عبر `storage.safeJoin(root, userPath)` التي:
1. تفك ترميز URL ثم ترفض `\0` ومحارف التحكّم.
2. تطبّع المسار بـ `path.posix.normalize`.
3. ترفض أي مقطع يساوي `..`.
4. تحلّ المسار بـ `path.resolve` ثم **تتحقق أن الناتج يبدأ بالجذر + فاصل المسار**.

الشرط الأخير هو المهم: فحص `startsWith(root)` وحده تخدعه `/data/storage-evil`.

بالإضافة: قبل الكتابة يُفحص أن الهدف ليس رابطاً رمزياً (`lstat`)، فلا يمكن
استغلال رابط قديم للكتابة خارج المجلد.

## ٧) ترويسات الأمان

**للوحة التحكم:**
```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
                         img-src 'self' data: blob:; connect-src 'self'; frame-ancestors 'none';
                         base-uri 'none'; form-action 'self'; object-src 'none'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Cross-Origin-Opener-Policy: same-origin
Permissions-Policy: geolocation=(), microphone=(), camera=()
```
`style-src 'unsafe-inline'` مطلوب لتبديل الثيم عبر متغيرات CSS في `style` — وهو
أضعف الاستثناءات أثراً ولا يسمح بتنفيذ سكربت.

**للمواقع المستضافة:** لا نفرض CSP (المواقع ملكك وقد تحتاج CDN)، لكن نفرض:
```
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Cross-Origin-Resource-Policy: same-site
X-Frame-Options: SAMEORIGIN   (للمشاريع الخاصة فقط)
```

## ٨) حقن SQL

**كل** استعلام يستخدم عبارات مُحضَّرة (prepared statements) بمعاملات موضعية `?`.
لا يوجد في المشروع أي بناء استعلام بدمج نصوص. أسماء الأعمدة في الترتيب (ORDER BY)
تُختار من قائمة بيضاء ثابتة، لا من مدخلات المستخدم.

## ٩) XSS

- الواجهة **لا تستخدم `innerHTML` مع بيانات من الخادم** إطلاقاً. كل النصوص تُدرج
  عبر `textContent`، وكل العناصر تُبنى بـ `document.createElement`.
- معاينة الملفات داخل اللوحة تعرض الكود كنص، لا كـHTML.
- المعاينة الحيّة للموقع تفتح في **أصل مختلف** (منفذ/نطاق آخر)، فحتى لو حوى الموقع
  سكربتاً خبيثاً فهو معزول عن اللوحة.

## ١٠) ما يُسجَّل وما لا يُسجَّل

**يُسجَّل:** الفعل، المستخدم، الوقت، عنوان IP، معرّف الهدف، النتيجة.
**لا يُسجَّل أبداً:** كلمات المرور، قيم الكوكي، رموز CSRF، مفاتيح API، محتوى الملفات.

## ١١) ما ليس مشمولاً (بصراحة)

- **لا مصادقة ثنائية (2FA)** في الإصدار الأول. إن عرّضت اللوحة للإنترنت، فأقوى
  إجراء إضافي متاح لك مجاناً هو وضع **Cloudflare Access** أمام `panel.example.com`
  (مجاني حتى 50 مستخدماً) فيصبح تسجيل الدخول برمز يصل إلى بريدك قبل الوصول للوحة.
- **لا فحص فيروسات** للملفات المرفوعة. أنت المستخدم الوحيد.
- **لا عزل sandbox لتنفيذ الكود** — لأنه لا يوجد تنفيذ كود أصلاً (وهذا هو المقصود).
- **النطاقات المخصصة تتطلب تحقق DNS يدوياً**؛ لا نصدر شهادات بأنفسنا (كلاودفلير تفعل).
